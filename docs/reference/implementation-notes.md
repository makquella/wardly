## Layout

Two independent packages, no monorepo tooling:
- `backend/` — Python 3.11 FastAPI app. Package is `app/`, entrypoint `app.main:app`. **Run all backend commands from `backend/`.**
- `frontend/` — one Electron app, `launcher/`: control panel window + always-on-top overlay window + tray; it runs the backend itself. `frontend/debug/` (index, overlay, script, styles) are legacy browser pages, debug-only: `/debug/` from a source checkout (`main.debug_pages_dir`), never frozen; nothing else of `frontend/` is served.
- `site/` — the project website: static landing (`index.html` + `styles.css` + `app.js`, no build; the landing stays an introduction — details go to their own pages: `heroes.html` lists the full-advisor heroes by position with their saves (the «Герої» menu item and a one-line strip on the landing point to it); `python scripts/build_site.py` (CI: `--check` in the backend job; it imports `backend/app`) writes the generated parts — the hero lists of `heroes.html`, one page per profiled hero `heroes/<slug>.html` and `en/heroes/<slug>.html` (lane last hits from the profile, then `advice_context.LH_RANGE_POINTS` × `hero_profiles.POSITION_PACE`, the HP/mana thresholds, the saves in `live_tools.USABLE_SAFETY`, the key fight abilities, the profile's note — Ukrainian notes in the script's `NOTES_UK`, a new profiled hero needs one), the static English copies `en/index.html` / `en/heroes.html` (from the Ukrainian HTML + `site/i18n-en.js`, strict JSON: every `data-i18n*` key must be there or the build fails) and `sitemap.xml` with hreflang pairs; rerun it after changing `index.html`, `heroes.html`, `i18n-en.js` or a profile. Every page is `<html data-static=uk|en>` with `data-alt-en` / `data-alt-uk`: the UK/EN switch opens the counterpart (keeping `?ref=`), a saved choice redirects to it, and the browser language never switches a page (search engines render in English); `tests/test_core_heroes.py` checks the lists and that every card's two pages exist; `app.js` works out the visitor's source (`?ref=<slug>` from the post's link, else the referrer's kind: search / a known site / other / direct; kept in sessionStorage for the tab), sends it once per visit (`POST /v1/hit` via sendBeacon) and points every download button at `api.luhovyimvp.dev/d/<source>` (no-JS fallback: the GitHub releases page); `robots.txt`, `sitemap.xml` (add new pages) and a `SoftwareApplication` JSON-LD in `index.html`; accent = the logo's red: `--accent` #f05560 for text/icons, `--accent-fill` #d23a46 under white button text, `--cream` #efe5d4; the share pages in `services/api/src/share.js` use the same), uk in the HTML and en in `app.js`; downloads resolve to the latest GitHub release; every picture is real: app windows (`site/assets/app/{uk,en}/`) and overlay cards (`site/assets/overlay/`) and review cards are shot from the real renderer on a demo backend with `scripts/site-shots/` (see its README); gameplay frames come from the Dota 2 Steam page and portraits from Valve's CDN (`game_frames.py`); no drawn mockups, no fake reviews; the screenshot windows stay flat (no 3D tilt or `scale()` on them: Chrome rasterizes such layers soft at 100 % zoom). Live at `https://luhovyimvp.dev` (GitHub Pages behind the Cloudflare proxy, SSL mode Full; canonical/og URLs point there). `site/changelog.html` («Що нового») is generated from `docs/release-notes/` by `python scripts/build_changelog.py` (template `scripts/changelog.template.html`; CI fails when it is stale — rerun it after adding release notes). Deploy notes in `site/README.md`; `.github/workflows/pages.yml` publishes it to GitHub Pages (manual run).
- `scripts/` — Windows build (`build-windows.ps1`) and smoke test (`smoke-windows.ps1`). `.github/workflows/dota-data.yml` refreshes `renderer/dota-data.js` weekly (PR on change) and fails when `build_dota_data.py --check-heroes` finds a hero missing from `HEROES`. The data workflows (this one and `stratz-builds.yml`) open their PRs with the workflow token (repo setting «Allow GitHub Actions to create and approve pull requests», on since 2026-10-05), and such a PR starts no CI — so each checks its new file before the PR (`node --test test/dota-icons.test.js`; `pytest tests/test_stratz_builds.py tests/test_game_plan.py tests/test_gold_tips.py`, where `test_the_bundled_file_is_sound` checks the shipped STRATZ file). Review the diff and run the backend tests locally before merging one.

holds no data, strict CSP with `script-src 'self'`, noindex; 404 while `ADMIN_TOKEN` is unset; the summary has `by_day` for its chart), `DELETE /v1/device/<install id>` (reports, shares, transfers, statistics; «Видалити мої дані на сервері» in Settings → «Ще налаштування», `deleteServerData` in main.js), admin list/fetch behind `ADMIN_TOKEN`, daily cron deletes reports after 180 days. Tests: `npm test` in `services/api/` (fake D1/R2, no workerd); local run: `npx wrangler dev`. `.github/workflows/api.yml` tests on PRs and deploys from `main` (creates the D1 database and R2 bucket if missing, applies `migrations/`, sets secrets from repo secrets `CLOUDFLARE_API_TOKEN`, `CLOUDFLARE_ACCOUNT_ID`, `TELEGRAM_*`, `API_ADMIN_TOKEN`). `site/privacy.html` describes what is sent — update it with any new upload.

## Backend tooling (run from `backend/`)

Create the venv once (gitignored at `backend/.venv`):
```bash
python3 -m venv .venv && source .venv/bin/activate && pip install -r requirements-dev.txt
```

Quality gate — this is the order CI (`.github/workflows/ci.yml`) uses:
```bash
ruff check .                 # lint
ruff format --check .        # format check
mypy app                     # NON-BLOCKING (see below)
pytest -q
python -m compileall -q app scripts packaging tests
```
After editing backend code, match the repo's Claude post-edit hook: `ruff check --fix . && ruff format .`.

Fuzzing: `python scripts/fuzz_live_gsi.py --payloads 10000 --seed N` sends broken GSI (dropped fields, wrong types, huge numbers, clock jumps, spectator blocks) through `/gsi` → overlay → `/gsi/status` → `/player` and fails on any 5xx or any error of the match recording (`PLAYER_SERVICE.observe_gsi`, which `/gsi` swallows to keep the live path up — a raise there silently loses the tick); `.github/workflows/fuzz.yml` runs it nightly with a new seed, `tests/test_fuzz_live_gsi.py` runs 250 payloads in CI. GSI numbers above `MAX_GSI_NUMBER` (10 000 000) or not finite count as missing (`gsi_state._optional_number`, `match_tracker._int`).

What GSI really sends (0.30.2): a *player* gets `provider`, `map` (with `radiant_score` / `dire_score`), `player`, `hero` (status flags, `talent_1..8`, `attributes_level`; no `aegis` field — the Aegis is `item_aegis` in a slot), `abilities` (Dota Plus `plus_high_five` / `plus_guild_banner` at level 1 among them — `skill_tips.not_hero_ability` drops them), `items` (`slot0-5` inventory, `slot6-8` backpack reported with `can_cast: true` although unusable — `last_moments.active_slot` keeps only 0-5 for ready items, regen and the wand; `stash*`, `teleport0`, `neutral0`; Bottle `contains_rune`), own-team `buildings` and `events` (`roshan_killed`, `aegis_picked_up`, `tip`…) — but only the blocks `gsiConfigText` in main.js asks for (`test/gsi-config.test.js` checks the list; `events` was missing until 0.30.2, so the Roshan/Aegis timers never got an event); `draft` is empty for a player; a player does get `minimap` with the enemy heroes in vision (`team` 2/3; checked on a real ranked match: all five enemies, no ally), and Dota adds `added` / `previously` diff blocks (the census skips them); `events` mixes `chat_message`, `tip`, `generic_event` and `bounty_rune_pickup` with the Roshan ones (`_objective_events` reads the last 100). Real payloads: `data/gsi_samples/real_player_hero_demo.json`, `real_player_ranked.json` (from open-source GSI libraries' test data, ids replaced). `app/gsi_census.py` (`GSI_CENSUS`, fed by `/gsi`) counts every field path seen in in-game payloads (names, counts, flags that were true, event types, minimap own/enemy hero counts and icon types, the enemies of the current match only — never values; item fields judged over the payloads with an item) and checks `FEATURES` (the paths each coach feature reads: ok / rare / missing); `GET /gsi/census` and `/diagnostics` `gsi_census`, so a problem report after one match shows what the game really sent. Saved to `PLAYER_DATA_DIR/gsi_census.json` (`save_due` from `/gsi`: every `SAVE_EVERY` 30 s while in-game payloads come, and once when the match stops sending them) and shown as `previous_run` while this run has no in-game payload (`main._census_for_report`), since a report is often sent after a restart. The launcher logs why it quits (`quitApp`: tray, Windows sign-out, a signal; «during a match» when one was going on). `/diagnostics` `player.last_recorded_match` (`PlayerService._last_recorded`): the newest match with a GSI timeline in counts only (samples, deaths, deaths with last seconds, advice, analysed, score), so a report sent the next day shows whether that game was recorded. Tests: `tests/test_gsi_census.py`.

Match recordings (0.32, `app/match_records.py`, `MATCH_RECORDS`): «Зберігати записи матчів тиждень» in Settings → «Ще налаштування» (`settings.matchRecords`, off by default; `DOTA_AI_MATCH_RECORDS` at start, `POST /settings/advice {match_records}` on change) → every live match of the player (not a spectated one) is written to `PLAYER_DATA_DIR/match_records/<YYYY-MM-DD_HHMM>_<matchid>.jsonl.gz` (+ a `.json` summary for the list): a `meta` line, `gsi` lines (`redact`: no `auth`, Steam/account id, nickname or chat events; one per game second, every change of game state / alive / hero, else at most every `RECORD_EVERY` 0.5 s of wall clock; buffered, appended as gzip members every 10 s; 60 MB cap) and `advice` lines (each new card: clock, decision point, action, reason, priority). `KEEP_DAYS` 7 (`prune` on configure and when switched on). `GET /match-records` lists them, `GET /match-records/<id>` serves one (ids of the list only); the launcher's list under the switch (`refreshRecords` / `renderRecords` in renderer/app.js) saves one to Downloads (`launcher:match-records`, `matchRecordsAction` + `downloadBackendFile` in main.js). The recordings replay through `simulate_live_gsi.py --session` after unpacking (`p` holds the payload). Tests: `tests/test_match_records.py`.

Live pipeline check: `python scripts/simulate_live_gsi.py [--lang uk --reasons | --session <raw_gsi_states.jsonl>]` feeds raw GSI (synthetic match or a recorded session) through `POST /gsi` → `/overlay/recommendation` with the scheduler clock on game time and prints every advice card — use it after changing live advice logic (replay-state simulations skip GSI normalization, where live-only bugs hide).

Run a focused test:
```bash
pytest tests/test_scheduler_spacing.py -q
pytest tests/test_evaluate_low_hp_gate.py::test_name -q
```

- Env flags live in `backend/.env` (see `.env.example`). `app/config.py` loads `backend/.env` then repo-root `.env`, both `override=False`.
- Dev server: `USE_LLM=false uvicorn app.main:app --reload` (from `backend/`).

### ruff: do NOT "fix" the ignored rules
`pyproject.toml` intentionally ignores `E501, SIM102, SIM103, F841`. These are tracked "Phase 0" soft-start debt that would need logic refactors in `advice_scheduler.py` / `post_laning_coach.py`. Don't collapse those nested ifs or remove the unused local in `evaluate()` unless you are doing the surrounding refactor. Line length is 100.

### mypy is non-blocking
Soft-start config: `check_untyped_defs=true`, `disallow_untyped_defs=false`, and CI runs `mypy app || true`. Don't treat mypy warnings as failures or gate on them; do annotate new code when reasonable.

## Backend runtime state is module-global (important for tests)

The app keeps live state in module-level singletons, not a DB:
- `ADVICE_SCHEDULER` (`app.advice_scheduler`)
- `MATCH_MEMORY` (`app.match_memory`)
- `COACH_SESSION_HISTORY` (`app.coach_summary`)
- `LIVE_SESSION_RECORDER` (`app.live_session_recorder`)
- `gsi_state` module globals (`_latest_raw_payload`, `_latest_normalized_state`, ...)
- `PLAYER_SERVICE` (`app.player_api`): SQLite store, match tracker, job queue (reconfigured per test)

`tests/conftest.py` has an **autouse** `reset_runtime_state` fixture that clears all of these before and after every test, and inserts `backend/` onto `sys.path` so `from app...` imports resolve. When writing tests, rely on this fixture. When reasoning about server behavior, remember these carry cross-request state. The `client` fixture returns a FastAPI `TestClient`.

**Advice language.** The pipeline produces English text only. `app/advice_i18n.py` translates the visible fields (`recommendation.action/reason`, `message`, `last_visible_advice`) at the API edge when the launcher asks with `lang=uk` (`/overlay/recommendation`, `/advice/recent`); history, logs and recordings stay English. When you add or change a visible advice string, add its Ukrainian to `_UK_EXACT` (or `_UK_PATTERNS` for texts with a hero/ability name) — `tests/test_advice_i18n.py` replays the fixtures plus mutated live GSI and fails on any visible text without a translation. Unknown text falls back to English, never half-translated.

«Чому ця порада?» (`app/advice_why.py`): one plain sentence per decision point saying what the coach saw (`WHY`, uk/en; every `DecisionPoint` but `NO_ADVICE` must have one — `tests/test_advice_why.py`); added as `why` to `/advice/recent` items (a folded line under each advice on Home; the open ones are kept by key because the list redraws every second) and to the review's advice log (`render_analysis`, from the stored `dp`). Keep it in sync with the rules in `decision_points.detect_decision_point` when they change.

Прокачка (`app/skill_tips.py`, `MATCH_MEMORY.skills`, live GSI only): `gsi_state` puts `read_skills(payload)` into `extra_context.skills` (hero level, levels spent in abilities + `talent_1..8` + `attributes_level`, the ability with `ultimate: true`, whether talent fields exist; NaN, infinity or huge numbers count as missing); `SkillTips` counts on changes from the first tick (a level gained must be followed by a level spent; a level spent it cannot see — an innate levelling with the ultimate — only moves the base, and a point «unspent» for `UNSPENT_STALE` 180 s is a miscount and resets), so errors fall on the side of silence. After `UNSPENT_WAIT` 15 s of clock unspent, once per hero level for 20 s: the ultimate at 6/12/18 («Вивчіть ультимейт: Omnislash…»; never Invoke, `FIXED_ULTIMATES`), else a level-10/15/20/25 talent when both of its pair are open, else «Не вкладено очко навичок»; after 10 without talent fields only the ultimate. Passed to `map_hint(skill=…)`, which shows it over any scheduled timer (the timers stay on the strip), never over Roshan/Aegis; `speak: True`; `over_plan: True` keeps it on the overlay over the game plan, and it shows with «Map timers» off too (`main._live_role_and_hint`). Tests: `tests/test_skill_tips.py`.

Pro skill order (`app/skill_build.py`): `OpenDotaClient.pro_skill_orders(hero)` reads the hero's recent pro matches (`/heroes/{id}/matches`, up to 8 tried for 5 with `ability_upgrades_arr`) → {orders (ability names; `ALIASES` makes Shadowraze 2/3 one skill), names (in-game `dname` from `/constants/abilities`, talents never), ids (the hero's ability ids)}, cached `opendota:pro_skills:<hero>` a week (`PlayerService.skill_build`, fetched on the job thread and in `_ensure_hero_meta`; `_hero_meta` carries it as `skills`). `skill_order` = the order the basic abilities are maxed (median point of the 4th level; maxed in half the games or more; ultimates, talents and innates drop out by themselves) + `first_agree`/`games`; `next_skill` = the first of that order below level 4 and below the hero-level cap ((level+1)//2). Live: the unspent-point tip becomes «Вкладіть очко в Blade Fury» + «Порядок прокачки в про-гравців на цьому герої: A → B → C» (`skill_tips._point`), the ultimate tip takes the in-game name (fallback `skill_build.label`: the GSI name table, else the raw name without the hero prefix from `read_skills` `hero_key`); the game plan adds «Прокачка в про: спершу A, потім B». The first point (0.40): `skill_order` also keeps `opening` {name, agree, games} — the skill 60 %+ of the pro games level first (`OPENING_AGREE`); a level-1 hero with nothing learned counts as owing a point from the first tick (`SkillTips.observe`), and `_point` at level 1 reads «Перше очко: Blade Fury — Про-гравці на цьому герої починають з Blade Fury (3 з 3 ігор)»; `map_hint` shows a skill tip before the horn too (negative clock or no role yet: the skill tip alone). Talents (0.24): `pro_skill_orders` also keeps `talents` {talent name: hero level of its row} from `/constants/hero_abilities` (row 1-4 → 10/15/20/25) and names them via `talent_label` (the constants leave numbers as `{s:…}` placeholders: «-{s:…}s Blade Fury Cooldown» → «Blade Fury Cooldown»); `skill_order` → `talents` {level: {name, label, picked, games}} where 60 %+ of the games that took that row agree (3+); the talent tip then reads «Талант 10-го рівня: про-гравці на цьому герої беруть «+200 Health» (5 з 5)». Data cached without `talents` is fetched again (`skill_build` in PlayerService, `force`); the ability names and the talent rows are optional requests (a failure keeps the order). Review: `trim_match` keeps the player's `ability_upgrades_arr` (`TRIM_VERSION` 3) → `facts.skill_upgrades` → `review_skills` (the first skill the player maxed vs the pros' when 60 %+ agree, 8+ upgrades) → `analysis.skills` and the finding `skill_first_max` (laning; focus `REQUIRES` skills); the review draws it as the «Прокачка» card next to the build (`skillsCard` in matches.js: the sentence, the pro order as numbered chips with the player's first skill marked, how many pro games agree). The site-shots demo backend has Juggernaut's pro data (`demo_data.PRO_SKILLS`) and a Healing-Ward-first order on the first match. Tests: `tests/test_skill_build.py`.

Situational item (`app/situational_items.py`): `PlayerService.next_item` puts first the item picked by how this match's deaths went (`MatchTracker.death_moments` → last_moments per death): 2+ deaths stunned or hexed on all but at most 1 recorded second of the last 5 (3+ seconds recorded; last_moments `held_s` — a mute alone never counts, the hero still moves and casts) → Black King Bar; 2+ burst deaths (`burst_s`) → Aeon Disk; not when owned or built into something (priced by the cached constants, else named without a price) — `why` + `count` on the item. `post_laning_coach._next_item_copy` says why («2 deaths under stuns with no free second, and Black King Bar stops that: N gold to go…», `SITUATIONAL_BECAUSE`, UK via `_UK_FUNCTIONS` `_situational_reason`), and the death screen adds «Чому Black King Bar: смертей під контролем — 2…». Cores only (the carry advisor). Counters to the enemy heroes (0.29.2): the player's GSI has no draft, so `gsi_config` asks for `"minimap" "1"` and `enemy_heroes.visible_enemy_heroes` reads the `npc_dota_hero_*` units of the other team (`team` 2/3) → `extra_context.visible_enemies` → `MATCH_MEMORY.enemies` (per match, up to 5) → `extra_context.enemy_heroes` (`main._with_enemies`); the priority is Linken's Sphere (2+ disabled deaths and a hero of `draft_analysis.TARGETED_DISABLES` seen — Beastmaster's Primal Roar, Doom, Duel, Reaper's Scythe, Charge of Darkness, Winter's Curse…, carry/mid/offlane) → BKB → Aeon Disk → Monkey King Bar vs evasion (carry, minute 15+) → Maelstrom vs illusions (carry, minute 12+: Phantom Lancer, Naga Siren, Terrorblade, Chaos Knight, Meepo) → Spirit Vessel vs healing (offlane, minute 12+; self-healers only — a healing support is in almost every lineup), the enemy and the spell named in the text («2 deaths under stuns against Beastmaster, and Linken's Sphere blocks Primal Roar»). Lineups (0.36): 3+ heroes of `draft_analysis.MAGIC_DAMAGE` seen from minute 14 → Pipe of Insight (offlane) / BKB (carry, mid), why `magic` («3 enemy heroes deal magic damage, and Pipe of Insight protects you from it», after the other rules); a support's «No save item yet» tip prefers the lineup's save item (`situational_items.lineup_save_item`, `PlayerService.save_item(hero, owned, enemies)`): Glimmer Cape against 3+ magic heroes, Ghost Scepter against 2+ `PHYSICAL_CARRIES` (`save_item_magic` / `save_item_physical` / `save_item_now_lineup` tips; no constants → no price). A support gets «{enemy} goes invisible: carry Dust or sentries» (`map_hints` `invis_dust`, no detection item). Break (0.55): `BREAK_PASSIVES` (Bristleback, Spectre's Dispersion, Huskar's Berserker's Blood) → Silver Edge for a carry or a mid from minute 18, why `break` with the passive in `spell` («Bristleback relies on Bristleback, and Silver Edge turns it off»). Draft read (0.55): `situational_items.draft_item` — the enemy counters without deaths and minute gates once 4+ enemy heroes are seen, cores only (`PlayerService.draft_item`, `main._live_role_and_hint` until `DRAFT_UNTIL`) → `LiveHintInputs.draft_item` → `RoleTips._draft_item`, once per match from 3:00 to 10:00 for 20 s, with the item icon («Проти їхнього драфту: Monkey King Bar»). Tests: `tests/test_situational_items.py`, `tests/test_counter_items.py`.

Less banal farm cards: the safe-farm category and the scheduler's heartbeat (`scheduler/heartbeat._heartbeat_copy`) use `post_laning_coach._situational_farm_copy` before the generic line (cores only: `main._with_coverage` puts `advisor_coverage` into the scheduler's state, and a support or safety-only hero keeps the plain line) — the player's kill streak 3+ (`extra_context.kill_streak` from GSI `player.kill_streak`: «Stay alive: you are on a 4-kill streak.»), the kill score gap 8+ after 12:00 (`team_name` + `radiant_score`/`dire_score`: behind → farm your half, ahead → take a tower), else the pace in numbers as the action («Keep farming: 512 gold per minute, 140 last hits at minute 21.»); the generic line only when none of it is known. `post_laning_farm_recovery` also puts its numbers in the action («Recover farm: 38 last hits at minute 18, a good pace is 98+.», `_farm_pace_copy`). The laning coach does the same: a lane under the pace in numbers (`laning_coach._pace_numbers`, last hits under the low end of `expected_lh_range`) counts as low farm and comes before the river/unknown-enemies position card (live GSI never shows enemies) → «Recover farm: 12 last hits at minute 5, a good pace is 18+.»; after minute 20 at half the pace the recovery reason names the side lanes and a camp between waves (`FAR_BEHIND_MINUTE`). Separate from the live advice path (it never gates or changes live advice):
- `app/player_service.py` (singleton `PLAYER_SERVICE` in `app/player_api.py`, routes under `/player`) links the Steam account (auto from GSI `player.steamid` the first time; manual via `app/steam_ids.py`: Friend ID, SteamID64, profile/OpenDota/Dotabuff URL, Steam2/3; vanity `/id/` URLs are rejected) and keeps the match table in SQLite (`app/player_store.py`, `PLAYER_DATA_DIR/coach.sqlite3`). Finishes on `POST_GAME`, a new match id, or 10 min without GSI (`check_stale`, called from `/gsi/status`); matches under 5 min or with no hero are dropped, and spectator GSI (watching a replay or a live game: per-team `player.team2/team3` blocks, `is_spectator_payload`) is ignored; the in-progress timeline is saved to disk and survives a restart.
- Game modes: `is_reviewable_match` (`dota_constants.py`) keeps only `REVIEWABLE_LOBBY_TYPES` × `REVIEWABLE_GAME_MODES` (All Pick, CM, RD, SD, AR, Least Played, CD, Ranked AP; unknown = yes). ## Local policy is authoritative; LLM is optional

Default `USE_LLM=false`. LLM providers only reword advice or run offline review. The backend always owns `decision_point`, `priority`, `time_window`, safety gating, and anti-spam scheduling — never let LLM output override these, and don't add hard LLM dependencies to the live path.

**Post-match AI coach** (separate from the live path and from `USE_LLM`): `app/coach_llm.py` (OpenAI-compatible chat client: **Gemini** (default, free AI Studio Flash tier, `generativelanguage.googleapis.com/v1beta/openai`, Bearer key, default `gemini-3.8-flash`), Groq and OpenRouter (free `openai/gpt-oss-120b`); JSON mode, `reasoning_effort=medium`, 120 s timeout. Free Gemini Flash models are often overloaded: on 503/429/404 it walks `FALLBACK_MODELS` (3.7 → 3.6 → 3.5 → `gemini-flash-latest`; Pro has no free quota), all busy → code `busy`, which the service retries by itself after 1/2/3 min. Google answers a wrong key with HTTP 400 → `invalid_key`) + `app/coach_review.py` (compact facts from the rendered review / career, numbers rounded as a person writes them → prompt → JSON answer → `FactChecker`: every number, `m:ss` time, hero and item in the text must appear in the facts, plus counts ≤12; 5-minute marks only as minutes («до 15-ї хвилини»), so "50 last hits" must still be a fact; failing sentences are dropped, >25 % dropped → one retry with the offending tokens → else error `unverified`). Compare models on one match: `scripts/compare_coach_models.py --model gemini:gemini-3.8-flash --model openrouter:stealth/space-bunny-alpha` (keys from env; `--data-dir`/`--match` for a real match from a copy of the app's database). The rules stay the source of every number: change facts or rules, not the checker, when a review is wrong. `PlayerService` runs it on its own `ai_jobs` queue, caches per match + language + facts hash (`coach:match:*`, `coach:career:*` in the `cache` table), shows the old review as `stale` while a new one is written, waits for OpenDota parsing (`waiting`) unless forced, and never auto-retries after an error except `busy` (1/2/3 min; 503 costs no quota). The key (and optional model id) is entered in the launcher (`/player/ai`, stored in the store's `meta` table, never returned — only `key_hint`) or taken from `GEMINI_API_KEY` / `GROQ_API_KEY` / `OPENROUTER_API_KEY` in `.env`. States in `detail.coach` / `career.coach`: `off | waiting | pending | ready | error | not_enough | none`. «Запитати тренера»: `POST /player/matches/{id}/ask` (`PlayerService.ask_match` → `coach_review.answer_question`, synchronous, 60 s client timeout; the launcher op allows 90 s) answers a free question from the match facts through the same `_generate` loop and `FactChecker` (one retry, then `unverified`); the question text is never trusted (the prompt tells the model to ignore instructions in it); the last 5 Q&A per match are kept in the cache (`coach:ask:<account>:<match>`) and returned as `detail.questions`. Tests: `tests/test_coach_ai.py` (`FakeLLM`; pass `llm=` to `PLAYER_SERVICE.configure`, run `service.ai_jobs.run_pending(until=float("inf"))`).

## Running the project

**Backend (dev)** — run from `backend/`:
```bash
USE_LLM=false uvicorn app.main:app --reload          # http://127.0.0.1:8000
python -m uvicorn app.main:app --host 127.0.0.1 --port 8000 --reload --no-access-log   # quieter variant
```
Port defaults to **8000**. With manual uvicorn it is a CLI flag; `backend/packaging/backend_server.py` (used by the launcher and the frozen exe) reads it from env via `app/config.py`: `DOTA_AI_BACKEND_HOST` (=`127.0.0.1`), `DOTA_AI_BACKEND_PORT` (=`8000`), `DOTA_AI_BACKEND_LOG_LEVEL` (=`info`). With `DOTA_AI_BACKEND_STDIN_CONTROL=1` it shuts down gracefully on a `shutdown` line or EOF on stdin — that is how the launcher stops it (no taskkill).

**GSI has no separate listener.** Dota 2 GSI is received by the `POST /gsi` endpoint on the **same** FastAPI server. The launcher writes `gamestate_integration_dota_ai_coach.cfg` into Dota 2's `gamestate_integration/` folder with `uri "http://127.0.0.1:<backend port>/gsi"` and rewrites it if the port changes (`gsiConfigText` / `syncGsiConfigPort` in `frontend/launcher/main.js`). Health check: `GET /health`.

**The launcher runs its own backend.** On start it picks a port (env `DOTA_AI_BACKEND_PORT` → last used port saved in settings → 8000 → any free port), spawns `backend/packaging/backend_server.py` (dev, `backend/.venv` Python, no `--reload`) or the bundled `dota-ai-coach-backend.exe` (packaged) hidden, forces `USE_LLM=false`, `LIVE_CONSERVATIVE_MODE=true`, and passes the port to both windows over IPC. A manual uvicorn on 8000 no longer conflicts (the launcher moves to another port), but you then have two independent backends — pick one entry point when debugging.

**Electron apps:**
```bash
cd frontend/launcher && npm install && npm run dev            # whole app: backend + overlay window + tray; Wayland/GNOME: `npm run dev:x11`
```

## Environment variables and secrets

Config is loaded by `python-dotenv` + `os.getenv` in `app/config.py` — **not** pydantic `BaseSettings`. Loading order: `backend/.env` then repo-root `.env`, both with `override=False` (frozen exe: `%APPDATA%\DotaAICoach\.env` instead). Consequence: **shell env vars always win**, and `backend/.env` takes priority over the root `.env` (root only fills gaps). When debugging "my key isn't picked up", check shell exports first, then `backend/.env`.

**No variable is required** — every `os.getenv` has a default; the backend boots with no `.env` at all.

## Doc checkout paths (resolved — no code change)

Earlier docs hardcoded a locale-specific absolute checkout path. It existed **only in documentation, never in code** — code was always portable:
- `backend/app/config.py:11` → `REPO_ROOT = Path(__file__).resolve().parents[2]`
- `frontend/launcher/main.js:8` → `REPO_ROOT = path.resolve(__dirname, "..", "..")`

So **do not touch code or add a `DOTA_AI_COACH_DIR` env var** — nothing reads it.

Fix applied (option b — repo-relative commands): the doc shell blocks in `README.md`, `docs/QUICKSTART.md`, `docs/REFERENCE_COMMANDS.md`, `docs/REPLAY_DEMO.md`, `frontend/desktop-overlay/README.md` (since removed) now use repo-relative `cd` (`cd backend`, `cd frontend/launcher`, …) instead of an absolute locale-specific path, so they don't depend on folder names like `Документи` vs `Documents`. `docs/PACKAGING_WINDOWS.md` uses repo-relative Windows commands (`scripts\build-windows.ps1`). When adding new docs, prefer repo-relative commands; use a `<repo-root>` placeholder with a one-line note only where an absolute path is genuinely unavoidable.
